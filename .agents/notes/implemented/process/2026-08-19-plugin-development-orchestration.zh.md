# Agent Note: 插件开发编排

Status: implemented

[English](2026-08-19-plugin-development-orchestration.md) | 中文

## 问题

插件开发指南分布在架构文档、扩展实操手册（cookbook）、包规则、测试策略和收尾 skill 中。这些真源分别定义了各自负责的主题，但仓库中没有一套工作流可以引导插件需求使用它们，也没有一套机制可以围绕任务依赖和文件所有权协调多个 coding agent（编程智能体）。

缺少这层引导时，插件扩展可能进入错误的开发路径；共享接口尚未确定，并行工作就可能开始；多个 agent 也可能各自修改集成文件或生成产物。即使各任务 lane 的校验分别通过，也不能证明组合后的代码树满足需求。

## 决策

仓库提供 [`dsh-plugin-development`](../../../skills/dsh-plugin-development/SKILL.md) skill，作为第一方和外部 DeepSeek Harness 插件扩展的薄编排层。该 skill 对请求的插件形式进行分类、选择现有权威指南、在设计阶段规划行为证据，并将评审和校验交给现有的专用 skill。

一个主 agent 负责范围、集成和组合后的结果。获得授权且适合委派时，主 agent 按可独立验证的交付物拆分工作，并为每项工作明确依赖、可写路径、共享文件和证据。在依赖实现并行推进之前，先确定共享接口和持久化事件定义。每个文件只有一个写入者，共享的集成文件或生成文件由一名指定负责人管理。

各任务 lane 交接后，主 agent 校验集成后的代码树。独立评审者接收原始需求、最终组合 diff 和仓库权威资料，而不是仅依赖实现者的总结。每次交接都记录仓库事实、修改路径、实际运行的校验和未解决风险。

编排 skill 链接架构、开发、测试、文案、评审和 pre-push 真源，不复制其中的要求。它不创建固定的 agent 角色集合，不要求小型改动也必须委派，不授予 Git 或外部写入权限，也不使用生成的计划和通过的门禁替代语义评审。

## 考虑过的替代方案

**将工作流加入根 `AGENTS.md`。** 即使大多数工作与插件开发无关，每个仓库任务也会承担额外的上下文成本，而且详细的引导会掩盖根文件中的常设规则。

**将包检查清单、测试矩阵和评审清单复制到一个 skill 中。** 重复的要求会偏离现有真源，并使更新工作依赖多个文案副本的同步。

**始终分配架构、实现、测试和文档角色。** 固定角色会给小型改动增加协调成本，并按标签而不是独立交付物拆分工作。有些插件改动只需要一个 agent；另一些改动则需要先确定共享接口，再设置多个实现任务 lane。

**允许每个任务 lane 更新聚合文件和生成产物。** 并发写入 lockfile、根配置、组合包配置、快照、Agent Note 和配对记录会产生冲突，也会使最终输出的所有权变得不明确。

**将任务 lane 级校验视为最终证据。** 各部分即使独立通过校验，也可能存在接口分歧，或在合并生成文件和组合配置变更后失败。

## 结果

插件扩展拥有一个可发现的开发入口，同时架构、开发、测试和评审事实仍各自保留唯一的权威来源。只有在交付物可以隔离时才启动多 agent 工作，集成后的结果也有明确的负责人和最终证据。

该工作流增加了前置分类和所有权步骤。主 agent 还必须协调各项交接并校验组合后的代码树，因此只有当独立工作的收益高于协调成本时，委派才有价值。
